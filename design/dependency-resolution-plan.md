## 0. Summary

Resolution runs in Cactup over data Cactarium already serves: `GET /packages/{o}/{n}/versions` gives every version with its thorns (CCL facts included) and its claims (dependencies with `needs`/`needed-by`/`alternatives`, `fork-of`, `incompatible-with`). What is missing is the reverse map from an installed repo (URL + commit) to its package, which every installation's base needs before "what is installed" means anything. A pure resolver module computes a plan (add / add thorns / upgrade / replace, each with why), the plan is shown and confirmed, and `add`'s existing machinery executes it: transitively added packages become ordinary `[[added]]` entries carrying only their `needs` thorns, so compose, refetch and remove keep working. Choices and durable overrides go into new top-level maps of `installation.toml` (no version bump for those; an installed flesh package bumps `INSTALLATION` to 4, §4.9). `sim export` gains the registered-package refusal and `--local`; `package init`/`stack init` generate manifests from the live installation; `--risky-allow-untrusted-artifacts` also asks admins' tokens for versions awaiting review.

## 2. The resolver (decided shape)

### 2.1 Data model (`src/deps/`, pure: no I/O, no printing)
```rust
pub struct PkgId(String);                         // "owner/name"
pub enum At { Version(TrackedVersion), Commit(String), Unknown(String) } // Unknown: a commit no version froze
pub struct Release { id: PkgId, at: At, commit: String, url: String, flesh: bool, yanked: bool,
                     pending: bool, thorns: Vec<ThornInfo>, claims: Vec<ClaimInfo> }
pub enum Origin { Base { repo: String }, Added, Planned }
pub struct Present { release: Release, enabled: BTreeSet<String>, origin: Origin } // what the installation has
pub enum Req { Range(TrackedReq), Commit(String) }
pub struct Why { by: PkgId, at: At, claim: String /* Dependency::label() */, thorns: Vec<String> }
pub enum Step { Add { release, thorns, why }, AddThorns { id, thorns, why }, Upgrade { from, to, thorns, why },
                Replace { base_repo, by: PkgId }, Keep { id, note } }
pub struct Plan { steps: Vec<Step>, choices: Vec<Choice>, notes: Vec<String> }
pub trait Facts { fn versions(&mut self, ids: &[PkgId]) -> Res<()>; fn release(&self, ..) -> ..; fn providers(&mut self, need: &Requirement) -> Res<Vec<(PkgId, String)>>; }
```
Base thorns from repos the lookup can't map become pseudo-packages `local:<name>` with `At::Unknown`, so conflicts see them.

### 2.2 Algorithm
Inputs: the named specs (package, `Req`, optional thorn subset), the present set (added packages, plus base repos mapped by the pin lookup, flesh included), overrides (§4.4), `--ignore-claim`s, `--upgrade`, `--no-deps`.
1. Apply overrides and ignores to every release's claims as they are loaded (drop, add, extra `needs`, "X satisfies Y").
2. **Seed** `chosen` with the present set. Present releases are fixed unless `--upgrade` and the plan touches them, or `--upgrade-all` (then each present package starts as a need for its newest release fitting every constraint). A **named** spec for a present package is never "fixed": it targets the newest release that fits, as re-adding does today (`add.rs:910-925`); "fixed unless `--upgrade`" applies to packages that were not named.
3. **Worklist of needs** `(target, Req, thorns, Why)`, starting with the named specs. Single-target dependencies first, to a fixpoint; then **any-of** dependencies one at a time in a fixed order (the dependent's id, then declaration order), re-running the fixpoint after each, so "already brought in" never depends on hash order.
4. For each need:
   - **Identity.** A chosen fork F of the target (a `fork-of` claim of F's chosen release) takes the need if `ForkOf::stands_in_for(dep, published(target))` (one more versions call for the upstream); else it is a conflict. An override "X satisfies T" takes it without a version check. The `needs` thorns must exist in whoever takes it.
   - **Version.** Add `Req` to the target's constraints. Keep the chosen release if it matches all of them; a fixed one that doesn't is a refusal (§4.5). Otherwise take the newest release that matches every constraint, has every required thorn, is not `state = invalid|upstream-missing`, and is not yanked unless a constraint is exact. A `#sha` need resolves through `/versions/<commit>` (an unreviewed commit of an untrusted package goes through `confirm_untrusted`, as `add` does since #32). `At::Unknown` satisfies a range with a note (misfit 5), and a `Commit` need only if it is that commit.
   - If a version changes for a package already expanded, restart from step 2. Constraints are keyed by their source `id@version`; when a source's release changes, its constraints are dropped, so a replaced release's constraints never refuse a consistent set. The work is bounded by a fixed step budget (and by the total number of candidate versions); past it, a deterministic "no consistent set" lists the live constraints and their sources.
   - **Upgrade, replace, stand-in carry the present set.** An `Upgrade` or `Replace` of a present package, or a fork standing in for one, enables the package's present enabled thorns plus the new `needs`, never `needs` alone (else `share_base_clone`, `add.rs:249-283`, refuses a clone whose other checkouts stay at the base's commit, and a fork leaves upstream thorns enabled, a conflict under decision 7).
   - **Libraries are placement, not needs.** A dependency with `into` (a library) is never pushed as a need: `resolve_libraries` keeps placing it, also under `--no-deps`. Its version constraint still enters the resolver, and two packages placing one library at incompatible versions (or at different `into` paths with different commits) are a conflict.
   - **Untrusted snapshots** (`#sha` or tip dependencies of untrusted packages) are collected by `Facts`, not confirmed inside the resolver: after a wave's renderer `shutdown_and_wait()`, `confirm_untrusted` asks for them, then the next wave starts.
   - **Pending releases** (served only under `--risky-allow-untrusted-artifacts`): "newest that fits" prefers approved releases; a pending one is taken only when a spec names it exactly or no approved release fits, and the plan lists every pending release it chose.
   - **Transitive.** Enable `needs − enabled`. For each newly enabled thorn, push the chosen release's dependencies whose `needed-by` contains it, plus those with empty `needed-by` when the package first enters. `--no-deps` pushes nothing beyond the named specs.
5. **any-of (D2):** an alternative present; else one already chosen by the plan; else the first listed among those conflicting with nothing present or planned. The choice and its rule are printed and recorded. No "fewest packages" rule.
6. **Conflicts after the fixpoint:** two enabled thorns of one name (case-insensitive) from different packages, pseudo-packages included; a fork and its upstream both present; any chosen release's `incompatible-with` matching another chosen release (both directions); a flesh dependency (`needs = []` on a flesh) not met by the installed or planned flesh or a fork standing in. (An unmet flesh dependency is first handled in step 4 like any need: the newest fitting flesh release is planned as a `Replace` of the base's `$ROOT` component; only when none fits does it get here.)
7. **CCL check on the delta (D3).** Every hard requirement (`ccl::Need` from `ccl::needs_of`, P1) of every newly enabled thorn must be met by the final set. Planned thorns use the registry's facts, present ones a local scan (`trim::thorn_facts`, made shared: parallel, with progress). This catches what the publish check doesn't cover: `--no-deps`, ignores, `#sha`/tip snapshots (never checked), base and local thorns. An unmet requirement always refuses (artifacts must be fully specified; open question 5): the refusal names the thorn, the requirement and the package whose manifest leaves it undeclared, and lists what `GET /providers` returns as `cactup add` lines (or says nothing provides it). Cactup never plans an undeclared provider. No defaults table.

Interrupt and progress: `versions` calls go in waves (each wave is the packages newly named), on `par::parallel_map`, one `progress::Line` per package under a `Headline` ("ask Cactarium"), the flag polled per item and between waves; each request has a timeout (blocking reqwest can't be interrupted mid-request). One `lookup` request per command, behind a `Line` too. **As built (P2), the resolver loads up front** everything that could come into play before it searches: every version of every package reachable through any claim from the named specs and, under `--upgrade`/`--upgrade-all`, from every present package. On a real ET installation with `--upgrade`, that is every base package's versions plus their closure: some 80-120 `versions` requests in a handful of waves, several MB to tens of MB. Then come the `#sha` snapshots those versions name, read one request at a time. So P3 puts every `Facts::load` wave and every `Facts::snapshot` behind the headline even when the command names a single package, and feeds `Facts::tick` (called every 64 search steps) into a line, so a search that runs long shows it is still going.

### 2.4 What is recorded (`installation.toml`, `INSTALLATION` schema 2; symbolic copies made it 3, flesh packages bump it to 4, see §4.9)
New top-level **maps**, so #31's put-back keeps them through an older binary's rewrite. Fields in `[[added]]` elements would be dropped, since put-back never enters arrays (misfit 18):
```toml
[added-for."et/carpet"]          # one per [[added]] package
requested = false                 # named on a command line, or brought in
by = ["max/z4c@1.2.0"]            # whose dependencies brought it in (informational)
for-commit = "<the [[added]] commit this entry was written for>"
[[added-for."et/carpet".choices]] # one per any-of this package was chosen for
dependent = "max/z4c"
alternatives = ["et/carpet", "et/cactuspugh"]

[claim-overrides."drop max/foo:dependency:et/bar"]   # key = the override's canonical text
kind = "drop"                     # drop | add | needs | satisfies
note = "et/bar's thorns ship with the flesh"
```
A choice is keyed by the dependent and its alternatives' ids (`ChoiceKey`), never by text. The key stops matching if the dependent's author edits or reorders the alternatives; `remove` then falls back to the first present alternative as the holder, which is safe. `choices` is an array, but it is safe: an older binary does not model `added-for` at all, so its put-back restores the whole top-level table, arrays included. Readers ignore `added-for` keys with no `[[added]]` entry (an older binary's `remove`); a package newly brought in (`requested = false`) never inherits such a leftover entry's `by` or `choices`. **Defaults that keep a named package safe:** each `added-for` entry also stores the `[[added]]` `commit` it was written for (`for-commit`); an entry that is missing (every installation written before this work) or whose `for-commit` differs from the `[[added]]` entry (an older binary re-added or upgraded it) means `requested = true`, so no orphan pass ever deletes a package the user may have named. `by` is informational (shown by `inst show`); dependents and orphans are computed from current claims (§4.2), never from `by`. If `added-for.*` entries are rebuilt whole by a writer, they go in `INSTALLATION.replace_whole` and the comment at `installation.rs:26-28` is updated. The shape pin of #31 fails: copy `current.toml` to a numbered fixture and re-pin, as its §2.5 says. Nothing new in `database.json`.

*As built (P3):* `added-for` is additive at schema 2 (no bump): an older binary's rewrite puts the map back, and absence means "named". `add` and `remove` replace only the entries they write for a new commit (`LockedInstallation::set_meta_rebuilding`, through `format::write_replacing_keys`, which names a sub-record by its keys so a package name with a `.` is one key); every other write, and an entry only edited at the same commit, keeps what a newer binary put inside it. `set_meta` drops an entry whose package has no `[[added]]` entry, so a later re-add never inherits it. The old shape pin is kept as `fixtures/formats/installation/v2-1.toml`.

*As built (P3), base extensions:* an `[[added]]` entry that only gives a base clone more thorns (it replaces nothing, and the base list has its clone under the same name from the same repository, compared with `same_repo_lenient`: `add::base_clone_of`, the one predicate `compose` and `present` share; a package from another repository that shares the name keeps its own source, and the fetch planner's conflict says so) lives in that clone at whatever commit the base has it (HEAD as the clone itself says, read with gix: a pull by hand moves it without the fetch record): `compose` writes its sections with the base's URL, branch and pin, an `add` only links its thorns (the clone is never fetched, pinned or fast-forwarded; `share_base_clone` is skipped for one at the clone's on-disk commit), and a refetch that moves the base moves them. `present` merges it into the base package (the first base clone of that package only), so a later dependent of the package is no clash; more thorns put the entry at the base's current release. A plan places the libraries of a release it brings in or moves, and of a present package it gives more thorns, those its new thorns need (a library claim whose `needed-by` names one of them); the entry records them. Given for a dependency and never named it records `requested = false`; naming any of its thorns later marks it named (nothing is installed again). `remove` runs it through `deps::plan_remove` as a node of its own, held only by dependencies (through forks and overrides too) that need one of its thorns (or name none), labeled with the base package's current release and its thorns; a dependency of the whole package stays with the base node. It goes as an orphan once nothing needs it: only those thorns leave the list, the base repo stays. A refetch whose new base drops the clone says so loudly: the entry then falls back to its own source, at the commit it was added at.

Known gap: an older binary that removes a brought-in package and then re-adds it by name at the same commit leaves an entry that still matches `for-commit` (`requested = false`), unless a newer binary wrote the file in between; only a marker inside `[[added]]` (dropped by any older write) could tell those apart.

*As built (P3), batch reads:* after the lookup and the HEAD reads, before planning, `add` and `remove` read every mapped base package at a commit no version froze, and every added package at a commit or tip, with `POST /packages/read` (S10): one request per 200 items, in package order, checked with `ReadRequest::validate`, waiting out 429s within the command's batch time (below, apart from the single reads' 5-minute wait budget; a Retry-After that would reach the batch deadline is not waited for, and what that request asked is read singly), shown as packages read out of all (an item dropped as unusable counts as done). An item read (`ok`) is no stand-in at all: its whole claims and thorns are the installation's, as for a frozen base package, so its `incompatible-with` meets what the plan adds, its dependencies hold back what the plan moves, replaces or removes (`remove` names it as a dependent), and its `fork-of` stands in or clashes as decision 7 says, renamed thorns or not; "Not checked"/"Cannot check" name only what stayed unread. `forbidden`, `not-found`, `bad-request` (with the server's words) and `upstream` leave it unread with the single read's reason, no single read made. `not-read` is asked again, round after round: 1.5 s later while some of it is still being read in the background (`in-progress`), 3 s later when none of it is (the server's network slots taken by other callers, or its time up), three such rounds in a row at most; then, or at the command's batch deadline, 5 minutes from its first batch phase and shared by every later one (checked before every request, and no wait between rounds or for the read limit is begun that would reach it; a phase that starts past it asks nothing), or after 30 rounds of a phase, what is still not read is left to the exact single reads below, made only when the plan depends on it. An item cactup cannot use (answered for another package or commit, the name's case aside; a version that is no release at that commit) is read singly and never asked in a batch again in the command, by a later prefetch either; an answer it cannot use (a body that does not parse, a count of items other than asked) ends batch reads for the whole command, as an older server does: everything in it, and everything later, is read singly. `remove` counts what comes back with a package that replaced a base repo, of the targets and of the packages that may be swept with them (never of a named package that stays): that base package at the base's pin, or, for a base that follows its branch, at the tip of the branch its restore will put the clone on (`fetch::known_after_restore`, the decision the restore's fetch plan makes: `!REPO_BRANCH`, else, no clone, the remote's default, else the branch a clone on that remote is on, else `known_branch` for a detached one), asked of the remote in one listing (that branch's tip, or the remote's default branch and its tip together); never the clone's HEAD, which is the replacement's. Upstream moving between that read and the restore is an accepted race: the restore takes the tip then. The remotes are asked on the network fan-out (32 at once), a line each, all within one 30 s window; Ctrl-C fails the command (checked even with nothing to ask). Only the bases of the targets and of what may be swept with them are read: of every added package the user did not name (`deps::may_bring_back`), not only of what the sweep takes with no base back, since a base that comes back takes a dependency over (before a fork or a satisfier of it, and before a later alternative of an any-of), so it can leave more to sweep, whose own bases come back in turn. That set holds every state of the sweep, so one round of reads does; the table checks that whatever a state takes along is in it, and that reading every base the case lists plans the same. Then one /lookup of every pin and one prefetch for all of them. A returning base holds a claim only if its release fits the claim's range or sha and it has every thorn the claim needs enabled (a claim naming no thorns, of a package cactup added, needs every thorn of the returning release; a base package's own such claim never asked for more than the base it came with); a dependent it meets is no dependent, one it does not still refuses the removal, and a refusal naming it says "(the base's, after the removal)". What cannot be read is said beside a refusal, tagged with the package that replaced it; when the removal goes ahead, a returning base of a target or an orphan that cannot be read is said on a "Not checked" line, and since it might need any orphan, every orphan's plan line says "unless a returning base repo needs it", so the confirmation (`--yes` without a terminal) covers it. An orphan that replaced base repos brings its bases back too, and they count for what is removed after it: the sweep runs again with them until the set going settles; should it come round to a set already seen instead (an orphan its own returning base holds), a package held in any of the states seen stays, never decided by the round. A dependency of a base package that names no thorns never holds an extension of the package it names: removing the extension gives back the base that package lived with. A Cactarium from before batch reads (404/405 with `api-generation` on the route) is read singly, as below, without a word; an answer without `api-generation` is the wrong-address error. Request counts (fake Cactarium; /resolve, /lookup, version lists, single reads, batches): on 20 base repos at unfrozen commits, `add` 1, 1, 1, 0, 1; `add` with a dependency on a base thorn 1, 1, 1, 0, 1; `--no-deps` 1, 1, 1, 0, 0; `--upgrade` 1, 1, 21, 0, 1; `remove` 0, 1, 0, 1, 1. Batch requests on 80 and 250 stand-ins: warm 1 and 2; cold (8 fetched per request, the rest ready on the next ask) 2 and 4, in two rounds.

*As built (P3), base packages at unfrozen commits (exact reads, Max's choice), what batch reads leave unread:* a base repo is read at its commit (`versions/{commit}`, always a full commit) up front only when the lookup says a version froze it. One at a commit no version froze, that no batch read, is a stand-in (`Present::stand_in`). Its thorns are known: every thorn its clone has at that commit (`resolution::scan_thorns` over the clone, when HEAD is at the stand-in's commit: what the crate's `ccl::scan_tree` finds, reading only each thorn's CCL files and never its sources, non-UTF-8 bytes read lossily as the crate does; the enabled ones carry the facts the tree has). Only its claims are unknown until it is read; the one thing it carries without a read is the lookup's `fork-of` (empty for an unfrozen commit on the real server), and whether it is the flesh is the lookup's word when the lookup says so, else the tree's. The resolver reads it there (`Facts::snapshot`) before the search, when the plan may depend on it, to a fixpoint, each once, named ones first and then the others, each group by id: a named spec; a need or any-of alternative of any release in the universe naming a thorn of it not enabled, or naming none (every thorn); a thorn name shared between one of its enabled thorns and a package the plan could bring in (whether it is a fork decides a clash). Thorns wanted of every present package (frozen, added or read, not only stand-ins) count, so the claims of a thorn the plan newly enables are followed; a read stand-in's claims count only for the thorns enabled or wanted of it, and are followed again when that set grows. Under `--no-deps` only a named one is read; a pseudo-package (`local:<name>`) never. The search itself never reads: every read it could need (stand-ins, commits claims name, libraries placed at a commit) is made before it, a read during it is a debug assertion (and an unread failure, never a wait), so its 30 s wall-time net counts no waiting.

What an unread stand-in means is narrow. A branch fails for want of its claims only when deciding it needs them: (a) enabling a thorn of it that is not enabled, (b) a dependency naming no thorns when that enables more, (c) bringing in, by a dependency, a package (not named, not present) with a thorn of the same name as one it has enabled, where its being a fork would make it stand in. Nothing else counts: not a fixed party, not a fork-and-upstream clash, not a failure at a release it moved to, not a commit mismatch, not a thorn its tree does not have (a plain "has no"). Such a failure's conflict is the decisions behind the need (and the stand-in's own, where it could move), never a verdict on the stand-in, so the search tries the alternatives as it would any other. A plan found is a plan, whatever branches failed that way. Its notes are worked out from the plan and the facts, never from the branches the search happened to explore: each release the search would have preferred to the one the plan has for a package it chose (newest first, a present one first where it may stay), or keeping a moved stand-in where it is, gets a note when what it asks itself needs what Cactarium did not read, naming every such stand-in in thorn-name order ("max/zza@2.0.0 was not considered: it needs StaticConformal of et/admbase#abababababab, and Cactarium did not read et/admbase there: …"; "keeping …"). A plan with such a note is always shown and confirmed (`--yes` without a terminal). The plan and its notes are the same whatever the package ids (`decisions_do_not_depend_on_ids` compares both). No plan, and some branch failed that way: `Refusal::Unreadable`, naming what needed which stand-in, for what, and why it was not read. A named spec never moves a base package without `--upgrade`, `--upgrade-all` or `--replace`.

Ways past are checked, never guessed. Every refusal that would suggest a flag (`--upgrade` for an installed package outside a range or lacking thorns, `--replace` for a clash or fork with a base repo, `--upgrade`, `--replace` or `--no-deps` for `Unreadable`) suggests it only when a search with it, on the facts already read (no read at a commit more; version lists may load), finds a plan: at most three such searches, each under the step limit. `--ignore-claim` ways are not searched (they drop the claim named). Naming an older version is never suggested: the search tries every version it could take, so naming one finds nothing it did not. With no flag finding a plan, `Unreadable` names the real cause: try again later (the read limit, a failing server or git host), push the commit (404), put it at a released version (403, an untrusted entry), or a commit readable by Cactarium (400, its own words).

Reads at a commit, as the server answers them (by status, matching its stable `error.code`): 404 `not-found` is no such commit ("et/x is at a commit unknown to Cactarium (is it pushed?)", which an unpushed local commit in a base clone now is); 400 `bad-request` is a package that cannot be read there (the server's message, "<slug> at commit <sha12>: …", is the reason; an abbreviated commit matching nothing is one too); 403 an untrusted entry; 429 the read limit; 502 `upstream` and other 5xx the git host or the server failing. Each leaves that one package unread, and the command goes on to the search; none fails `add` or `remove` on its own. On a 429 the registry waits: `Retry-After` seconds (at most 120), else (an older server) until 60 s after the window this command's first answer opened, on a line with the time waited so far, interruptibly, each read retried at most twice; past 5 minutes of waiting in all, the reads still to make are unread at once. `remove` reads a base package at an unfrozen commit that cactup gave more thorns (their claims decide what may go); other base packages keep the short "not checked" line. Where HEAD is in each clone cactup fetched is read once per command, in parallel, on a line, and serves both reading the base and placing what the plan adds.

*As built (P3), restoring base clones (0fed45f, c480d2b):* `remove` restores a base clone cactup detached for a replacement (its HEAD detached at the removed entry's commit, `restore_plan`'s `ours`): the fetch planner treats it as cactup's own checkout and puts it back on a branch, never as a user's detached checkout to keep. A fetch's recorded branch from a pinned fetch is a label (a tag or the pin's name), never a branch to align to. The branch a clone goes back to (`fetch::branch_to_follow`, shared by the planner and the forced skip) is, in order: the thornlist's `!REPO_BRANCH`; the recorded branch, if the last fetch was not pinned; the clone's `default_branch`; the remote's default branch, asked of the remote; and only then the pinned label. A silent change: a clone made pinned whose label named another real branch now goes back to the remote's default branch, not to that one; the thornlist's `!REPO_BRANCH` still wins. *Review fixes:* the recorded branch counts only from a record of the same URL, and the clone's own refs only when its `origin` is the list's remote (a forced clone whose URL changed asks the new remote). A forced clone gets its record, so a user-detached clone forced with `refetch -f` goes back to the branch its last fetch followed. The remotes are asked after the plan's probes (a forced repo's in a pass of their own), on a network fan-out 32 wide (not the 8-wide disk pool), a headline over a line each, all within one 30 s window, quietly (ssh in batch mode with a 30 s connect timeout unless the user has their own ssh command, no credential prompt). Unanswered, the clone goes back to the label, said on its line and in `refetch -n` (and in the error if `align` then fails on a tag); with no label either, `plan` skips the clone as detached, as before cactup asked remotes, and a forced fetch fails it saying why; `remove`'s restore refuses it before the prompt. Ctrl-C fails the plan. Each ask's scratch repository goes in a per-process directory (`$TMPDIR/cactup-remote-asks-<pid>`); one given up on stays until its thread ends, and the first ask of a later process removes the directories of processes no longer running. `add` and `remove` plan only the clones they touch, so no other is probed or asked, and the fetch under the lock is compared with the one before the prompt without its notes' words. A branch an align puts the clone on gets its upstream (`branch.<b>.remote`/`.merge`) when it has none, as a clone does; the config keeps its mode (any config edit does, the origin's re-pointing too), and a write that fails leaves the fetch done and recorded, with a warning on its line. The probe phase still draws a plain item per repo (no `Line`): it has no phases or numbers to show.

*As built (P3), requests:* an added package is read at its commit, a base extension not at all; a frozen base repo at its commit; whole version lists only for what may move (`--upgrade`/`--upgrade-all` read them for every present package instead). Base packages at commits no version froze, and added packages at a commit or tip, are read in batches (above): on 20 such base repos, `add` makes 1 /resolve, 1 /lookup, 1 version list, 0 single reads and 1 batch request; with a dependency on one base thorn the same; `--no-deps` 1, 1, 1, 0, 0; `--upgrade` 1, 1, 21, 0, 1; `remove` 0, 1, 0, 1, 1. A cold base (the server reading in the background, `in-progress`) takes a round more, 1.5 s later, while some of it is still being read: on 80 stand-ins 2 requests in 2 rounds, on 250 4 in 2; a read that takes three asks, 4 rounds; slots busy twice, 3 rounds, then all read. Batch reads end 5 minutes after the command's first batch phase (requests and waits together, every phase of the command sharing that one deadline) or after 30 rounds of a phase, and what is left is read singly. Worst case, a command spends 5 minutes on batch reads and then up to 5 more waiting for the read limit of single reads (the single reads' budget is apart from the batch deadline), plus the remote asks: 30 s for all of a phase's (32 asked at once; one that would start after the 30 s is not asked, and its clone falls back as if unanswered). A read at a commit answered 400, 403, 429 (after waiting) or 5xx, or 404 for no such commit, leaves that package unread; it never fails the command, and neither does a batch answer cactup cannot use (its items are read singly). Frozen base repos are read singly, batch reads or not: on 5 registered base repos at frozen commits, a plain `add` with no dependencies 1, 1, 1, 5 (no batch); with one dependency 1, 1, 2, 5; `--upgrade`/`--upgrade-all` 1, 1, 7, 0; `remove` 0, 1, 0, 6. *Older server only* (no batch reads), on 20 base repos at unfrozen commits: `add` and `add --no-deps` 1, 1, 1, 0; `add` of a package whose dependency names a thorn of one base package not enabled 1, 1, 1, 1; `add --upgrade` 1, 1, 21, 0; `remove` 0, 1, 0, 1 (the added package). A package clashing by name with 14 such base packages reads each once (14 reads, one 429 waited out); a plan needing 15 reads makes 16 requests at a commit, waiting once. Not bounded there: added packages at commits or tips are read up front (their claims gate moves and removals), so 13 or more of them meet the server's limit and leave some unread.

*As built (P3), what cannot be read:* an added package whose release Cactarium cannot give (its version no longer served, a commit it cannot read, a read refused) hides what it depends on: `remove` refuses beside one, `add` refuses to move present packages beside one (one it moves, re-adds or replaces itself excepted) and warns otherwise; `--no-deps` gets past both. Base packages whose dependencies are unknown (stand-ins not read, unread) are normal: one line when `add` moves a present package, and one short line with no count when `remove` removes anything (their claims being what is unknown, nothing tells which could claim what goes); neither refuses for them. The lookup's `fork-of` targets are read as fork claims in every form (`@range`, `#sha`, bare).

*As built (P3), the server and the client:* a 404 or 405 from `/lookup` or `/providers` means an older Cactarium only when the answer carries `api-generation` (the real server's API fallback does). An answer from a Cactarium route without it (the base compared as a URL: scheme, host and port, then a path prefix) is no Cactarium's when it says there is no such route (404, 405, 501: a wrong path prefix, a plain web server), on any route, and the message names the `cactarium-url` knob; a 5xx without it is the server or a proxy in front of it failing now (Apache's own 502/503/504 carry no generation): a read at a commit stays unread with that reason, and a publication or refresh says it may have reached Cactarium all the same. Older Cactarium: `add` names `--no-deps`, under which every base repo is taken as no registered package's; no `/providers` keeps the unmet-requirement refusal and says the providers cannot be listed. Every client request, its whole answer read, runs on a thread of its own and gives way to Ctrl-C within 50 ms; none starts once Ctrl-C was pressed, and a publication or refresh interrupted in flight says it may have reached Cactarium. Requests made to resolve dependencies (`Client::patient`) wait up to 120 s for the head of an answer (30 s to connect) and for each stall of the body; every other request keeps the download client's 30 s. A client with a whole-request limit (`inst show`'s 5 s) gets reqwest's per-request timeout, which bounds the whole answer, body included.

## 4. Commands

### 4.1 `cactup add` (`args.rs:325`, `add.rs`)
New flags: `--upgrade`, `--upgrade-all` (every present package is movable, not only those the plan touches), `--no-deps`, `--ignore-claim OWNER/PKG[:KIND:TARGET]` (repeatable), `--yes`, `--dry-run`. `resolve_all` becomes "load releases plus lookup, then `deps::resolve`". The plan's steps turn into `Wanted` entries; `Replace` uses the existing `replaces` path (`--upgrade` implies it for the repos it names). `reuse_base_clone`/`share_base_clone` cover "more thorns of a base package at the same commit". Writes `added-for`.

### 4.2 `cactup remove`
Dependents and orphans are computed from the **current** claims of every present package (one `versions` wave plus the base lookup, with progress), with overrides and the any-of choices applied, never from the stored `by`. Offline (Cactarium unreachable), `remove` refuses and names `--no-deps` (remove exactly what was named, no dependents check, no orphan removal) as the way past. Refuses to remove a package another added or base package depends on, naming the dependents, with `--no-deps` as the way past. Packages the removal orphans (`requested = false`, no remaining `by`, computed to a fixpoint) join the plan as `remove` steps, each with why ("brought in by max/z4c, no longer needed"); the plan is shown and confirmed as in §2.3, and `--no-deps` leaves orphans installed (open question 9).

### 4.3 `install owner/stack`, `inst refetch`, `import`
- **Stack install / refetch to a stack:** no resolution (a release is frozen). After composing, run the check (steps 6-7) over the result and print problems as warnings naming `cactup add --upgrade <pkg>` or `cactup claims override …`. They never fail the command. Base mapping comes from `RepoPin.cactarium` once the server fills it (S2), else from the lookup.
- **`import`:** unchanged except §4.8; a sim pins everything.

### 4.4 New `cactup claims` (D4)
- `claims override drop OWNER/PKG:KIND:TARGET [--note]`: drop a dependency, `incompatible-with` or `fork-of`.
- `claims override add OWNER/PKG --dependency TARGET --needs A,B [--needed-by T]`: add a missing claim.
- `claims override needs OWNER/PKG:dependency:TARGET THORN…`: add missing `needs` thorns.
- `claims override satisfies X Y`: X stands in for Y. X is `owner/pkg` or `local:<name>` for an unregistered repo of the installation (misfit 15).
- `claims list` (the overrides plus the any-of choices); `claims override --remove KEY`; `claims check` (steps 6-7 over the whole installation, read-only; what refetch and stack install print).

Carried: into exported sims as `provenance.extra["claims-overrides"]`, informational (misfit 4); into generated manifests as comment lines.

### 4.5 Refusals and their way past (user-visible text: no §-refs)
| Situation | Message ends with |
|---|---|
| Present release outside a new range | "Pass --upgrade to move it, or --ignore-claim max/z4c:dependency:et/carpetx" |
| Same thorn name, two packages | "Pass --replace to use et/carpetx in place of base repo carpetx, or `cactup claims override satisfies local:carpetx et/carpetx`" |
| `incompatible-with` | "--ignore-claim et/a:incompatible-with:et/b (this command) or `cactup claims override drop …` (for good)" |

### 4.6 `sim export` / `sim pack` / `sim publish` (D6)
After the existing pins (`export.rs:58-80`), one lookup of every git pin. Refuse, naming each repo: uncommitted changes ("commit and rebuild"), unpushed commits ("push, then `cactup inst refetch`"), a repo that is no registered package's ("push it and register it with `cactup package init <repo> --publish`, or fork a registered package"), untracked/`ignore` thorns, and download components not reviewed by Cactarium (misfit 13; S9: a reviewed download, matched by URL and sha256, passes). Each refusal also says "or --local for a sim for your own use". `--local` replaces `--allow-dirty`/`--allow-unpushed` (open question 3); it needs no marker in the file, because Cactarium refuses exactly the sims that needed it. `RepoPin.cactarium` is filled from the lookup on git pins only: `owner/pkg@<exact version>` for a commit a version froze, a bare `owner/pkg` for any other commit (the pin's `commit` field already gives it). *Decided by Max, relayed by the Cactarium session 2026-11-13, replacing an earlier "add the commit version": no `#` stamps in `.sim` or stack pins; the sha would only repeat `commit`, at the cost of a format bump and a consistency check.* Both labels are valid at format 1; crate PR #5 validates pin labels as exactly those two forms. The crate also refuses `#` in `[provenance] base`: if export ever fills `base` (it writes `None` today) from an installation whose base is a stack at `#commit`, it writes the bare stack slug instead. A download whose hash the build never froze (today only a warning, `export.rs:63-77`) now refuses without `--local`: there is nothing to review. Download pins go through S9's lookup. `sim publish` (in `import.rs`, rewritten by #39) runs the same lookup check before uploading. *Update from the Cactarium session (Max, 2026-11-16):* a `.sim` `[[input]]` with `url` and `sha256` needs an approved download too, exactly like a download pin; the server refuses an upload with an unapproved input, naming `cactup download submit <url>`, and a rejected input download makes a tag's freeze invalid. Export writes inputs without a `url` today, so only a hand-edited sim carries one, but `sim publish` and export's check send such inputs in the lookup's `downloads` list beside the download pins and refuse the same way.

### 4.7 `cactup package init [REPO]` / `cactup stack init` (D5)
- **package init:** REPO is a repo of the active installation (default: the one containing the current directory). It writes `cactarium.toml` at the repo root, for review; it refuses to overwrite without `-f`. `[package]`: `name` (the repo name, lowercased; `--name`), `owners` (whoami, S5; `--owner`), `root`/`arrangement` from `ccl::scan_tree`'s layout. For each requirement the repo's own thorns don't meet: the installed thorn meeting it (capabilities and functions: the one in the active config's built ThornList; implementations: if several from different packages, a commented TODO `any-of`, misfit 10), mapped to package and version. One `[[dependency]]` per provider package and distinct `needed-by` set, with `needed-by` always explicit. Ranges are `~X.Y.Z`, or `track:~X.Y.Z` on a track; `--exact` writes `=X.Y.Z`; a provider at a commit no version froze, or in an unregistered repo, becomes a TODO comment. **Forks:** for each present package sharing thorn names with the repo, if one of its versions' frozen commits is an ancestor of HEAD (new `fetch::git::is_ancestor`) and the thorns match → `[[fork-of]] target = "<pkg>@=<newest contained version>"`, missing thorns as a TODO. **Smells → TODO comments only:** an `#include` whose path leaves the thorn's directory into another thorn (sources scanned in parallel, with progress); a generic `Driver` inherit next to one driver's headers; repo thorns not built here (as a possible `exclude-thorns`); a flesh fork in use (possible flesh dependency). Overrides go in as comments. Written by template, then checked with `Manifest::from_repo_file` (TOML serialization can't carry comments).
- **stack init:** writes `cactarium-stack.toml` with `extends = [<the release the installation is on>]`, `[[stack.pin]]` for base repos whose commit differs from the release's pins, and added packages: `[[override]] repo = "<repo>" package = "<pkg>@=<version>"` (the crate's `Override` requires `repo`) where they replace a base repo, pinned CRL sections in a generated thornlist otherwise. Packages at a tip or at a commit no version froze (which `compose` writes unpinned for tips, `add.rs:62-76`) are pinned at their fetched commit in the generated thornlist, never `@=<version>`. A base that is a stack tip (`@head`) has no release for `extends`: refuse, naming `cactup inst refetch --release` to move onto a release first. Plus informational `[[dependency]]` entries: for each package another installed package depends on, the range and `needs` those declarations give, with a comment naming each declaring package (misfit 7, open question 10). It refuses dirty/unpushed repos like export.
- **`--publish`** never writes. Package: requires `cactarium.toml` committed and pushed (refusing with the git commands), then registers (S4) or refreshes (exists). Stack: `--publish --version V` uploads the definition through the existing `publish_stack`.

### 4.8 `--risky-allow-untrusted-artifacts`, second meaning (D7)
With the flag, every request carries `x-cactarium-include-unreviewed: true` and the stored token, if any, whether or not the user is an admin (update from the Cactarium session, per Max, server PR Cactarium#3). Without the flag, GETs stay anonymous. The server decides what the header gets: with an admin token, releases awaiting review plus entries awaiting their first review; for anyone else, releases awaiting review of public entries when the site's untrusted-tips setting is `allow`, otherwise nothing changes. A response that serves anything unreviewed carries `x-cactarium-unreviewed: true`, and Cactup warns on it as it does for untrusted tips (the `confirm_untrusted` shape from #32). A release with `review = "pending"` is printed in red ("awaiting review: nobody has approved it"). Unreviewed sims download to `<v>.unreviewed.sim`, which the offline fallback never uses; the name comes from #39's `simfile_cache_path` (which every cache read and write goes through, sim segment included), and "unreviewed" from the `/resolve` answer's `x-cactarium-unreviewed` header, since `fetch_published` picks the destination before downloading (`Client::resolve` must stop discarding headers). Help text (with #32's text as the base):
> Take what nobody has reviewed without asking: a branch tip (@head, @master) or a commit no published version names (#commit) of a stack or package not trusted by Cactarium, and, with an admin's token (cactup login), versions still awaiting review. Such code may fetch and build anything. The warning is still printed.

### 4.9 Flesh packages (decision 6)
The "existing `replaces` path" does not cover the flesh (finding 12), so this is its own work (phase P3b):
- **Replacement is keyed on the flesh, not on collision:** a flesh package replaces every base component for which `fetch::is_flesh` holds, whatever its name or URL. `add` drops its flesh refusal (`add.rs:632`) for that path.
- **`compose`** emits a `$ROOT` section for the flesh package, with the base flesh component's checkout list (Makefile, lib, src, …) at the package's URL and commit, and drops the base's flesh components.
- **Links:** the new clone goes in `repos/`, the root's links (already links into `repos/`, `UNTRACKED_FLESH`) are re-pointed to it; `remove` re-points them to the base's flesh clone (fetched again if pruned).
- **Rebuild notice:** the plan and the command's summary say every config of the installation needs a rebuild.
- **Format: `INSTALLATION` 3 → 4.** (Master's `inst cp --symbolic` took 3, for `linked-to`.) The `[[added]]` element needs a flesh marker (and its checkout items), and put-back never enters arrays: an older binary would compose it as "no thorns, drops nothing" and silently put the base flesh back. Following the library precedent (`installation.rs`, the comment on `INSTALLATION`): v4 adds the marker; the v4 → v3 down-step answers `CannotExpress` when a flesh package is present, so only installations with one get v4 (sticky afterward), and an older binary refuses them rather than corrupting them. New `v4` fixture, re-pin, spec §2.5 matrix.

*As built (P3b):*
- **Record.** `[[added]]` gains `flesh`, the base flesh's items at the root when the package was added (`Makefile`, `lib`, `src`, …), in list order; empty means no flesh package, so the list is the marker. `replaces` names the base's flesh repos too, which keeps `base_clone_of`, the restore and `returning_base` on the existing replacement paths. A base with no flesh has nothing to replace: adding a flesh to it is refused, naming the package that needs it when a dependency brings it in (re-adding one keeps the items recorded before). `INSTALLATION` stays not `frozen_read` (only login binaries write it), but its down-chain is complete, so the v4 → v3 step is what writes every record without a flesh package at the version it had (the write rule's "oldest version that holds the content"). The old shape pin is kept as `fixtures/formats/installation/v3-1.toml`. The recorded items are frozen at add time: a refetch to a base whose flesh has more items at the root does not pick them up (re-add the package, or remove and add it).
- **Keyed on the flesh.** `compose` drops every component of every base repo with a component for which `fetch::is_flesh` holds (`add::base_flesh_repos`), arrangement thorns of such a repo included, matching the resolver's flesh replacement, which removes the whole package. The base being composed onto decides, so a refetch to a base whose flesh is named otherwise still loses its flesh. `present` leaves those repos out when a flesh package is added, so the resolver never sees two present fleshes. The package's section is written before its thorns', at `!TARGET = $ROOT`, the items on the `!CHECKOUT` line (fetched, never built), `!NAME` its clone. A flesh package from another repository named like the base's flesh clone (a fork at `…/flesh.git`) is refused: the clone would have to move between two repositories, and the base's flesh comes back there on `remove`. Sharing the clone name is not supported in this phase.
- **At most one.** The resolver's `TwoFleshes` (two brought in at once) and `replace_fleshes` (one coming in takes the present flesh's place) already were the rule; `add` now carries out `Replace { replaced: Added }`: the displaced flesh package's `[[added]]` and `added-for` entries go, and its clone stays on disk (said, with the prune hint). `add` does not sweep the displaced package's own brought-in dependencies; `remove` of their dependents does, as for any orphan. An added flesh package moved to a release that is not a flesh is refused (remove it first).
- **Dependents of the displaced flesh.** A flesh coming in never takes the place of a present flesh (an added flesh package or the base's own) that a package staying still needs: `Refusal::FleshHasDependents` lists each dependent with what it asks. A fork standing in for the displaced flesh, or an override naming a satisfier, meets the need, as elsewhere. The claim binds as passive claims do, so `--no-deps` gets past; that way is suggested only when a search with it finds a plan. Table cases `flesh-displaced-*`.
- **Links.** The fetch's link pass re-points the root's links into the new clone (`add`) or the base's flesh clone (`remove`, which restores the base's flesh repos under their current names: `touched` is `replaces` plus the current base's flesh repos; a pruned clone is cloned again, at the base's pin). A base with no flesh (after a refetch) gets the root's links into the removed package's clone taken away, said in one line: they are links only, so no user file is lost, and the root then matches the base. Before the fetch, `RootLinks` saves every link at a root checkout of the old and the new list and puts them back unless the new list is written (every one it can, each failure said), so Ctrl-C (or a failure) part way through the link pass never leaves some links at one flesh and some at the other. A symbolic copy needs nothing more: its root links are relative links of its own (not copy links), its new clone is real, and its base flesh clone keeps its copy links; `lock_sources` and `Cow::before_replace` stay on both paths.
- **Rebuild.** The plan's line (`FLESH_REBUILD`) is shown by `add` when `plan.rebuild` and by `remove` when a flesh package goes, whenever the plan is shown; the last line is `Rebuild every config for the new flesh, e.g. …` (`… for the base's flesh, …` after a remove). For that to hold, `build::source_delta` reads a flesh from a repo absent from the last build's record as a swapped flesh (`SourceChange::swapped`, said as "the flesh now comes from repo X"): a realclean, not an incremental build of the new thornlist. Only a flesh that could be probed counts. The flesh is where the root's `Makefile` links into `repos/` (`fetch::source_heads`, probed even when the list does not name it), so a config built from a thornlist of its own, which keeps naming the base's flesh, sees the swap too, in `build`, `config delta` and the submit warning alike. A config with no `sources` record still cannot see a swap.
- **Remove's dependents.** `returning_base` reads only the arrangement thorns of a replaced repo, so the base's flesh coming back never holds a flesh dependency: removing a flesh package needed by another package is refused (`--no-deps` gets past), even when the base's flesh would meet it.

## 5. Misfits (for the Cactarium session and Max)

1. **fork-of range.** The spec's generation section writes `<package>@~<series>`; D5 writes `<pkg>@~<version>`. *Decided:* `=<newest upstream version the fork contains>` (a tilde range would claim later patches the fork lacks); fix the spec.
2. **Requirement semantics fork three ways** (trim, server, soon resolver). *Proposal:* move `Need`/`needs_of`/`meets` into the crate's `ccl`; all callers use it.
3. **Base isn't mapped to packages** (finding 6), so "installed stays fixed" has no packages to fix, and every base thorn would read as a foreign same-named thorn. *Proposal:* S1 + S2; a blocker for P3.
4. **Overrides "carried into exported sims":** sims declare no dependencies and import never resolves, so there is nothing to act on. *Proposal:* informational `provenance.extra["claims-overrides"]` (no format bump). In manifests they are comments, since they are about other packages' claims.
5. **Installed at no version** (ET `install master`, stack `@head`, custom lists, `add …@head`/`#sha`, unmapped commits): a range can't be checked. *Proposal:* it satisfies a range with a printed note (installed stays fixed); a `#sha` need only by that commit.
6. **Conflict granularity.** "Two packages with a thorn of the same name", but Cactup adds single thorns (`owner/pkg/Thorn`, `AddedPackage.thorns`). *Decided:* the conflict is on enabled thorns; fork and upstream always conflict.
7. **A `[stack]`'s `[[dependency]]`** (`needs` optional) has no resolution meaning, and stacks are installed frozen. Nothing checks stack releases. *Decided:* the resolver ignores stack dependencies; stack install and refetch run the check as warnings; `stack init` writes them as information (what could be swapped in, e.g. a fork), taken from the installed packages' own declarations; the server checks stack releases (S8).
8. **Upgrades.** The spec says resolution runs on "upgrades"; Cactup upgrades a base by `inst refetch --release`. *Proposal:* only `add --upgrade` re-resolves; refetch re-checks and warns.
9. **One unclaimed provider:** D3 covers "several". Snapshots (`#sha`, tips) are never checked server-side (`tracker.rs:1109` is the only call), so unclaimed requirements are real there. *Decided:* zero, one or several, it refuses; cactup never fills in an undeclared dependency.
10. **"The installed thorns that actually met each requirement":** for implementations several compiled thorns can (Carpet and PUGH both implement `driver`), and nothing records which a run uses. *Proposal:* capabilities and functions from the active config's ThornList (CST allows one provider); an ambiguous implementation becomes a TODO `any-of`, never a claim.
11. **Flesh packages.** No CCL requirement points at the flesh, so generation never writes a flesh dependency, and `add` can't install a flesh (finding 12). *Decided:* generation writes a TODO for a flesh fork; `add` can install a flesh package, replacing the base's flesh, and the resolver plans that replacement when a flesh dependency is unmet (open question 6).
12. **`--publish` vs "written for review, the user commits"**, and no registration API (only the web form `/new/repo`). *Proposal:* `--publish` never writes; it registers an already committed and pushed manifest (S4).
13. **Pins that can never be a package:** download components (pinned by sha256, `export.rs:62-76`), `!TYPE = ignore`/untracked private thorns. *Decided:* private/untracked thorns refuse without `--local`; downloads pass once reviewed by Cactarium like a package submission (S9), else refuse without `--local` (open question 4).
14. **`--ignore-claim` on an any-of:** the `:target` is ambiguous. *Proposal:* it matches any alternative's `owner/name`; the kind may be `dependency`, `incompatible-with` or `fork-of`; it covers every version.
15. **"X satisfies Y" when X is no registered package** (an unregistered fork in the base). *Decided by Max (2026-11-23):* `local:<name>`.
16. **The review page's `cactup import et/foo@1.2.0`** fits sims only. *Proposal:* show `cactup add` for packages, `cactup install` for stacks. The header must also reveal pending *entries* (`public_entry` hides them). Unreviewed sims stay out of the offline cache.
17. **A version can pass the check against a target awaiting review** (`deps.rs` `target_version`: `review IN ('approved','pending')`), which ordinary clients can't see. Resolution then fails with "no served version in range". *Cactarium session's answer (2026-11-13):* neither; fit it into #6's wait logic. A dependent whose check passes only through a pending target waits (left unread, retried) until the target is reviewed: approved → it freezes normally; rejected → re-checked against approved versions only.
18. **`[[added]]` is an array** that #31's put-back doesn't protect. *Proposal:* new maps (§2.4), no `INSTALLATION` bump.
19. **"Driver inherit next to one driver's headers"** needs to know which thorn provides a header; `ThornFacts` scans `USES INCLUDE` but not `INCLUDE[S] HEADER: … in …`. *Agreed with the Cactarium session:* add `provides-includes` to `ThornFacts` (additive, serde default) for new versions; frozen non-curated versions are not re-scanned (curated ones get it on `reapply`); where a version lacks it, the smell falls back to by-path includes.
20. **One flag, two meanings:** an admin reviewing also skips untrusted-tip prompts. Accepted as decided; noted in the help text.

## 10. Open questions for Max (with a recommendation)
1. **`--upgrade` scope:** *Decided (Max, 2026-11-13):* `--upgrade` moves only the packages the plan touches; `--upgrade-all` also moves every other installed package to its newest release that fits.
2. **No terminal:** *Decided (Max, 2026-11-13):* refuse unless `--yes` when the plan goes beyond what was named, printing the plan and naming `--yes` and `--dry-run`.
3. **`--local` replaces `--allow-dirty`/`--allow-unpushed`:** *Decided (Max, 2026-11-13):* `--local` only; both old flags are removed with no shim.
4. **Download and private/untracked components in sims:** *Decided (Max, 2026-11-13):* private/untracked/`ignore` thorns refuse without `--local`. A download component pinned by sha256 is allowed, but only once Cactarium has reviewed that download (URL + sha256) through a review like a new package submission (S9); an unreviewed download refuses without `--local`. Refusing all downloads would reject pretty-bhns, which is too strict.
5. **Exactly one provider for an unclaimed requirement:** *Decided (Max, 2026-11-13): "Artifacts MUST be fully-specified."* Cactup never fills in a dependency nobody declared. Any unmet requirement refuses, whatever the number of providers, naming the package whose manifest leaves it undeclared and listing the providers found as `cactup add` lines.
6. **Flesh forks as dependencies:** *Decided (Max, 2026-11-13):* flesh replacement in `add` is part of this work ("the flesh is mostly just a repo checked out like any other"). A flesh package replaces the base's `$ROOT` component through the existing `replaces` path: its clone goes in `repos/` and the root's links point into it (the flesh is already a link into `repos/`, see `UNTRACKED_FLESH`); `remove` restores the base's flesh. A plan that needs a flesh the installation lacks plans its replacement like any other step. The plan output says every config needs a rebuild.
7. **Conflicts on enabled thorns, not whole packages:** *Decided (Max, 2026-11-13):* two enabled thorns with one name conflict; a fork and its upstream always conflict.
8. **fork-of range:** *Decided (Max, 2026-11-13):* `=<newest contained version>` (exact), neither `~<version>` nor `~<series>`, both of which claim later patch releases the fork lacks.
9. **`remove` of a depended-on package:** *Decided (Max, 2026-11-13):* refuse naming dependents, `--no-deps` to force. Packages the removal leaves unneeded (brought in as dependencies, never named, no remaining dependent) are removed in the same command: shown as a plan and confirmed like `add`'s (no terminal: refuse unless `--yes`).
10. **`stack init`:** *Decided (Max, 2026-11-13):* exact-version overrides and pinned extra sections (what installs), plus `[[dependency]]` entries as information: what forks or other versions could be swapped in with a good chance of the stack still working. Each entry carries the range and `needs` that the installation's packages actually declare for that package (several declarations: one entry each, a comment naming the declaring package); a package nothing depends on gets none, its pin covers it. Nothing is invented. Exact pins are always required: every component of a stack is pinned exactly, and a `[[dependency]]` entry never stands in for a pin. Resolution still never runs at stack install.
